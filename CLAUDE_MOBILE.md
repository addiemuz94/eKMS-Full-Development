- **Digital Key hardware-feasibility test tooling (mobileApp only, deliberately experimental)** — a throwaway "Experimental" tab (`SuperAdminCompanionApp.kt`) hosting `DigitalKeyTestScreen.kt`, which deliberately and temporarily crosses boundaries #1/#2 (see `CLAUDE.md`) at the user's explicit request, purely to evaluate two candidate phone-as-key designs on real hardware before any decision is made — **not** a settled architecture change, see the Known issues entry below for the exact framing to use. **Option A** (`nfc/OptionACardUidHostApduService.kt`): `NfcAdapter` reader mode captures a real card's raw UID (`Tag.getId()`, held in-memory only via `CapturedCardUidStore` — no persistence, no encryption), replayed by a `HostApduService` as application-layer APDU response data after AID selection. Checked current Android docs before building, not assumed: standard HCE has no public API to control the low-level ISO 14443-A anti-collision UID — it's randomized per-tap by the phone's NFC controller by design (Android's own HCE guide: "NFC readers should not depend on the UID of HCE devices as a form of authentication or identification"); Option A can only ever affect the APDU-layer response, never the anti-collision UID itself, and this is surfaced as an explicit on-screen warning rather than silently assumed to work. **Option B** (`nfc/OptionBDigitalKeyHostApduService.kt`): a locally-generated UUID (`DigitalKeyIdentityStore`, plain SharedPreferences, not derived from any physical card) replayed the same way, on a separate AID from Option A's. Also checked, not assumed: AID-conflict/default-app resolution only applies when two services register the *same* AID — since A and B use different AIDs under `category="other"`, both can be registered and enabled simultaneously with no forced system default; the in-screen enable/disable toggles are a testing convenience (`PackageManager.setComponentEnabledSetting`) rather than something the platform requires. Added `android.permission.NFC` + `<uses-feature android:name="android.hardware.nfc">` to `AndroidManifest.xml` — mobileApp had zero permissions declared before this. `shared`/`terminalApp`/`web`/`backend` untouched. Pairs with a separate, not-yet-built terminalApp-side raw-reader-frame diagnostic screen (see `CLAUDE_TERMINAL.md`) for the actual test. Verify: `:mobileApp:assembleDebug` passes; installed and launched on a real device (Samsung SM-A176B) for the user's hands-on test. **This fundamentally requires that real-hardware test to mean anything — code-level verification alone cannot confirm either option actually works.**
